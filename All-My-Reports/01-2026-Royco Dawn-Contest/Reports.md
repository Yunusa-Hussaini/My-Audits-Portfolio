## Title:
## [H-01] Critical Accounting Desync Allows Junior Tranche To Steal Senior Tranche Yield In Same Block
Target: https://github.com/roycoprotocol/royco-dawn/blob/main/src%2Faccountant%2FRoycoAccountant.sol#L565-L574

## Summary:
Royco’s tranche accounting allows Junior Tranche (JT) to capture yield generated by Senior Tranche (ST) when multiple accounting sync operations are executed within the same block.

When block.timestamp does not advance between consecutive sync calls, the protocol falls back to instantaneous yield share logic. This allows ST appreciation to be redistributed to JT without any time-weighted accrual, breaking tranche isolation and causing incorrect NAV attribution.

The issue is located in RoycoAccountant._previewSyncTrancheAccounting() inside the same-block yield distribution in RoycoAccountant._previewSyncTrancheAccounting() inside the same-block yield distribution branch.
```solidity
// RoycoAccountant.sol

 // Compute the time weighted average JT share of yield
                uint256 elapsed = block.timestamp - $.lastDistributionTimestamp;
                // If the last yield distribution happened in the same block, use the instantaneous JT yield share. Else, use the time-weighted average JT yield share since the last distribution
                NAV_UNIT jtGain;
                if (elapsed == 0) {
                    // Get the instantaneous YDM output and ensure that JT cannot earn more than 100% of senior appreciation
                    uint256 instantaneousJtYieldShareWAD =
                        IYDM($.ydm).previewJTYieldShare($.lastMarketState, $.lastSTRawNAV, $.lastJTRawNAV, $.betaWAD, $.coverageWAD, $.lastJTEffectiveNAV);
                    if (instantaneousJtYieldShareWAD > WAD) instantaneousJtYieldShareWAD = WAD;
                    jtGain = stGain.mulDiv(instantaneousJtYieldShareWAD, WAD, Math.Rounding.Floor);
```

## Finding description:

_previewSyncTrancheAccounting() distributes ST yield to JT when ST gains occur and no impermanent losses remain.

The logic checks:
```solidity
elapsed = block.timestamp - lastDistributionTimestamp
```
When multiple sync operations are executed in the same block, elapsed == 0. In this case, the protocol uses previewJTYieldShare() to immediately compute JT’s share of ST yield.

This allows the following sequence:

1. Accounting sync initializes timestamps

2. ST raw NAV increases

3. Another sync call is executed in the same block

4. Yield is redistributed using instantaneous JT share

5. JT captures ST yield without any time-based accrual

There is no block-level or monotonic time protection preventing repeated same-block redistribution.

## Impact Explanation:

1. This issue breaks core accounting assumptions of the protocol:

2. Junior Tranche can receive yield it did not earn

3. Senior Tranche LPs lose proportional rewards

4. NAV calculations become distorted

5. Yield attribution invariants are violated

Since Royco relies on synchronized accounting for minting, redemptions, and coverage enforcement, this misallocation can propagate into long-term economic inconsistencies and unfair value distribution between users.

## Likelihood Explanation:

1. Exploitation is highly likely because:

2. The accounting sync functions are publicly accessible

3. No privileged role is required

4. No special timing or MEV is needed

5. The behavior is fully deterministic and repeatable

6. An attacker only needs to trigger multiple accounting sync calls within the same block after ST NAV increases.

## Recommendation:

1. To prevent same-block yield redistribution:

2. Skip yield share application when block.timestamp == lastDistributionTimestamp

3. Track lastDistributionBlock and disallow duplicate yield application within the same block

4. Enforce monotonic time progression before applying yield share logic

This ensures yield is only redistributed after real time advancement and preserves tranche isolation.
