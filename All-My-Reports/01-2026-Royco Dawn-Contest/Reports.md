## [H-01] Critical Accounting Desync Allows Junior Tranche To Steal Senior Tranche Yield In Same Block
Target: https://github.com/roycoprotocol/royco-dawn/blob/main/src%2Faccountant%2FRoycoAccountant.sol#L565-L574

## Summary:
Royco’s tranche accounting allows Junior Tranche (JT) to capture yield generated by Senior Tranche (ST) when multiple accounting sync operations are executed within the same block.

When block.timestamp does not advance between consecutive sync calls, the protocol falls back to instantaneous yield share logic. This allows ST appreciation to be redistributed to JT without any time-weighted accrual, breaking tranche isolation and causing incorrect NAV attribution.

The issue is located in RoycoAccountant._previewSyncTrancheAccounting() inside the same-block yield distribution in RoycoAccountant._previewSyncTrancheAccounting() inside the same-block yield distribution branch.
```solidity
// RoycoAccountant.sol

 // Compute the time weighted average JT share of yield
                uint256 elapsed = block.timestamp - $.lastDistributionTimestamp;
                // If the last yield distribution happened in the same block, use the instantaneous JT yield share. Else, use the time-weighted average JT yield share since the last distribution
                NAV_UNIT jtGain;
                if (elapsed == 0) {
                    // Get the instantaneous YDM output and ensure that JT cannot earn more than 100% of senior appreciation
                    uint256 instantaneousJtYieldShareWAD =
                        IYDM($.ydm).previewJTYieldShare($.lastMarketState, $.lastSTRawNAV, $.lastJTRawNAV, $.betaWAD, $.coverageWAD, $.lastJTEffectiveNAV);
                    if (instantaneousJtYieldShareWAD > WAD) instantaneousJtYieldShareWAD = WAD;
                    jtGain = stGain.mulDiv(instantaneousJtYieldShareWAD, WAD, Math.Rounding.Floor);
```

## Finding description:

_previewSyncTrancheAccounting() distributes ST yield to JT when ST gains occur and no impermanent losses remain.

The logic checks:
```solidity
elapsed = block.timestamp - lastDistributionTimestamp
```
When multiple sync operations are executed in the same block, elapsed == 0. In this case, the protocol uses previewJTYieldShare() to immediately compute JT’s share of ST yield.

This allows the following sequence:

1. Accounting sync initializes timestamps

2. ST raw NAV increases

3. Another sync call is executed in the same block

4. Yield is redistributed using instantaneous JT share

5. JT captures ST yield without any time-based accrual

There is no block-level or monotonic time protection preventing repeated same-block redistribution.

## Impact Explanation:

1. This issue breaks core accounting assumptions of the protocol:

2. Junior Tranche can receive yield it did not earn

3. Senior Tranche LPs lose proportional rewards

4. NAV calculations become distorted

5. Yield attribution invariants are violated

Since Royco relies on synchronized accounting for minting, redemptions, and coverage enforcement, this misallocation can propagate into long-term economic inconsistencies and unfair value distribution between users.

## Likelihood Explanation:

1. Exploitation is highly likely because:

2. The accounting sync functions are publicly accessible

3. No privileged role is required

4. No special timing or MEV is needed

5. The behavior is fully deterministic and repeatable

6. An attacker only needs to trigger multiple accounting sync calls within the same block after ST NAV increases.

## [H-02] Protocol Fee Accounting Drift Allows Repeated Fee Accrual on Same Yield.

Target: https://github.com/roycoprotocol/royco-dawn/blob/main/src/accountant/RoycoAccountant.sol#L580-L586

## Summary:

Royco’s accounting logic allows protocol fees to be accrued multiple times on the same underlying yield when repeated accounting sync operations are executed without corresponding NAV movement.

Because protocol fees are derived from transient gain values during _previewSyncTrancheAccounting() and not tied to monotonic NAV checkpoints, repeated sync calls can cause cumulative fee drift. Over time this results in protocol fee over-accrual that exceeds the actual yield generated by the system.

This breaks fee accounting invariants and causes protocol-level balance distortion:

```solidity
// RoycoAccountant.sol
  // Compute the protocol fee taken on this JT yield accrual (will be used to mint shares to the protocol fee recipient) at the updated JT effective NAV
                    jtProtocolFeeAccrued = (jtProtocolFeeAccrued + jtGain.mulDiv($.jtProtocolFeeWAD, WAD, Math.Rounding.Floor));
                    jtEffectiveNAV = (jtEffectiveNAV + jtGain);
                    stGain = (stGain - jtGain);
                }
                // Compute the protocol fee taken on this ST yield accrual (will be used to mint shares to the protocol fee recipient) at the updated JT effective NAV
                stProtocolFeeAccrued = stGain.mulDiv($.stProtocolFeeWAD, WAD, Math.Rounding.Floor);
```

## Finding Description:

Protocol fees are computed inside _previewSyncTrancheAccounting() whenever ST or JT gains are processed.

Relevant logic pattern:

Yield is calculated from NAV deltas

Protocol fee is derived from the calculated gain

Fee values are accumulated into stProtocolFeeAccrued and jtProtocolFeeAccrued

No persistent “fee already accounted” checkpoint exists

This creates the following flaw:

Execution Path

1.ST raw NAV increases due to external yield

2.Accounting sync is executed protocol fee is accrued from this gain

3.No state enforces that this gain has already been fee-processed

4.Another accounting sync is executed without NAV change

5.The same yield path is re-entered

6.Protocol fee is accrued again on the same economic gain

Because fee accrual depends on transient gain computation instead of monotonic yield checkpoints, repeated sync calls result in cumulative over-accounting.

There is no guard that enforces:

One fee accrual per realized gain

Or monotonic fee settlement boundaries.

## Logic Proof Example:

Assume:

ST gain = 100 units

Protocol fee = 10%

No impermanent losses exist

First sync:

ST gain processed = 100 Protocol fee accrued = 10 ST effective NAV updated

Second sync (no NAV change):

Accounting path is re-entered Gain path is recalculated Protocol fee accrued again = 10

Result:

Total protocol fee recorded = 20 Actual economic gain = 100

This violates the invariant:

Protocol fee must never exceed configured percentage of realized yield.

The drift compounds as sync operations repeat.

## Impact Explanation:

Protocol fee accounting can become inflated beyond actual realized yield.

Because fee accrual is triggered repeatedly on the same underlying NAV gain, the protocol may mint or record fees that were never economically earned. Over time, this leads to:

Overstatement of protocol revenue

Incorrect liability accounting

Drift between real asset value and internal accounting

Broken invariant between yield generation and fee collection

Potential downstream insolvency risk during redemptions or fee withdrawals

Since Royco relies on synchronized accounting for minting, redemptions, and tranche NAV calculations, this inconsistency propagates across the system and directly impacts financial correctness.

## Likelihood Explanation:

Exploitation likelihood is medium to high because:

1. Sync functions are publicly callable

2. No privileged role required

3. Behavior is deterministic

4. No special timing required

Repeated sync operations naturally occur via deposits, withdrawals, and system interactions
Even benign user activity can unintentionally trigger this drift.

## Proof of Concept:

The issue can be reproduced using the following deterministic sequence:

Initial State:

1. Senior Tranche (ST) has deposited liquidity

2. Protocol fee rate is non-zero

3. RoycoAccountant has already been initialized

4. No impermanent loss is present

## Step 1 — First Accounting Sync:

Call accounting sync:

```solidity

```

Result:

1. lastFeeTimestamp is updated

2. Current ST NAV is recorded

3. No protocol fee is accrued yet

## Step 2 — Senior Tranche NAV Increases:

External yield is realized by the protocol:

1. ST raw NAV increases due to yield generation

2. No accounting sync is executed yet

This yield is now pending fee processing.

## Step 3 — Second Accounting Sync (Fee Accrual Trigger)

Call accounting sync again:

```solidity
syncAccounting()
```

Result:

Fee is calculated using:

```solidity
fee = (currentSTNAV - previousSTNAV) * protocolFeeRate
```

Protocol fee is accrued

lastFeeTimestamp is updated

## Step 4 — Third Accounting Sync Without New Yield:

Call accounting sync again without any additional yield generation:

```solidity
syncAccounting()
```

Observed Behavior:

1. Fee logic is executed again

2. The same NAV delta is reused

3. Protocol fee is accrued a second time

4. No check exists to ensure the yield was already processed

## Result:

Protocol fees are accrued multiple times from the same underlying yield.

This produces accounting drift where:

1. Protocol revenue grows

2. Real asset value remains unchanged

3. Internal accounting becomes inconsistent

This behavior can be confirmed by tracing fee accumulation variables inside the accountant after each sync call.

This behavior can be verified by instrumenting logs around the protocol fee accumulator inside RoycoAccountant and observing repeated increases after consecutive sync calls without intermediate yield generation.

## Recommendation:

To prevent protocol fee drift:

1.  Introduce monotonic fee settlement checkpoints

2. Ensure fees are accrued only once per realized NAV delta

3. Track last processed NAV values for fee computation

4. Prevent repeated fee application on unchanged accounting state

This guarantees protocol fees remain bounded by real yield generation.

## [H-03] NAV Conservation Can Be Bypassed via Order-Dependent Delta Processing.

Target: The issue lies in this code block inside _previewSyncTrancheAccounting, where NAV changes are applied and the NAV sum invariant is enforced: https://github.com/roycoprotocol/royco-dawn/blob/main/src%2Faccountant%2FRoycoAccountant.sol#L467-L553

## Summary:

_previewSyncTrancheAccounting() enforces a NAV conservation check, but the internal accounting logic is order-dependent. Because ST and JT deltas are applied sequentially using different logic branches, two equivalent raw NAV changes can produce different effective NAV distributions between tranches, while still passing the conservation invariant. This allows NAV to be redistributed incorrectly between ST and JT without triggering any revert.

## Finding Description:

_previewSyncTrancheAccounting calculates tranche NAV changes in two main steps:

JT delta application logic: Applies junior NAV changes first, absorbing losses or realizing gains, potentially affecting coverage and JT self-loss.

ST delta application logic: Applies senior NAV changes next, including coverage shifts, loss recovery, and final yield distribution.

The logic branches differently based on whether there is a loss or gain for ST and JT. Since improvements or losses in value trigger different internal adjustments. for example, ST covering JT loss, or JT contributing to loss absorption, multiple sequences with identical raw NAV deltas can produce distinct effective NAV results.

Because the final check only enforces:

```solidity
require((_stRawNAV + _jtRawNAV) == (stEffectiveNAV + jtEffectiveNAV));
```

Both valid and invalid NAV allocation paths from a business logic perspective may pass this check as long as the total sum matches, even if internal distribution between ST and JT is inequitable or unintended.

This means that:

1. Effective NAV distribution can be manipulated via specific delta paths.

2. NAV conservation alone is insufficient to guarantee correct accounting behavior.

3. A market participant or MEV strategy could influence NAV allocation without violating the raw sum check.

## Impact Explanation:

This logic flaw can break the economic assumptions of the protocol:

1. Incorrect NAV splits between ST and JT: Two sequences yielding the same net NAV can result in different allocations, potentially favoring one tranche over the other.

2. Unintended economic outcomes: ST or JT participants might be credited or debited in a way that doesn’t reflect the actual economic contribution or losses.

3. Deeper accounting inconsistencies: Downstream contracts rely on effective NAV for mint/redemption pricing, yield calculations, and coverage enforcement. Divergent allocations can propagate errors into those flows.

4. MEV or Sequencing Exploits: Malicious or sophisticated actors could construct operations that create beneficial NAV allocation drifts while still satisfying the invariant check.

Even though the sum of NAVs remains constant, so the invariant is not technically violated, the internal distribution of value between tranches can be incorrect, thus violating the protocol’s intended economic guarantees.

## Likelihood Explanation:

1. The issue does not require privileged access.

2. It stems from the design/ordering of internal logic branches.

3. Specific sequences of operations. e.g., LP actions, yield distributions, external market changes can trigger mixed delta paths.

4. Because operations such as preOpSyncTrancheAccounting and post operation paths are publicly callable and part of normal lifecycle flows, the condition is real world reachable with crafted sequences making the likelihood moderate to high in complex interactions.

## Proof of Concept:

Below is an example scenario that illustrates the inconsistency:

1. Set initial raw NAVs: ST = 1000, JT = 1000

2. First adjustment:

ST experiences a small positive gain

JT experiences a small positive gain

These yield a resulting effective NAV.

3. Alternate operation ordering:
JT takes its delta first

ST takes its delta second

This produces a different effective NAV distribution.

4. Both scenarios yield the same (stRawNAV + jtRawNAV), so the require invariant check does not fail.

5. Yet the internal ST/JT effective NAV distribution differs demonstrating a drift between sequences.

## Recommendation:

To mitigate:

1. Make NAV allocation logic path-insensitive: Ensure that the order of applying ST and JT deltas does not change the resulting distribution.

2. Validate individual component invariants: Instead of only checking the raw sum, also validate that internal allocations match expected business logic (e.g., no double counting or path dependency).

3. Modularize delta applications: Compute all deltas first, then apply a consistent settlement logic that is order invariant.

4. Write explicit unit tests covering alternative delta sequences: Test that different sequences of operations yield identical effective NAV results.

## [H-04] Mixed Delta Accounting Paths Allow Silent NAV Redistribution Between Tranches While Passing Conservation Invariant

Target:
RoycoAccountant.postOpSyncTrancheAccounting()  
https://github.com/roycoprotocol/royco-dawn/blob/main/src%2Faccountant%2FRoycoAccountant.sol#L143-L266

## Summary:

Royco’s post operation accounting logic allows tranche balances to become internally inconsistent when Senior ST and Junior JT NAV deltas are applied together in mixed execution paths.

Although a global NAV conservation check exists, the internal accounting logic updates ST and JT balances independently using combined delta values. This allows value to shift silently between tranches while still passing the invariant.

As a result, tranche-level accounting can become corrupted even though the total NAV check succeeds.

```solidity
// RoycoAccountant.sol

 /// @inheritdoc IRoycoAccountant
    function postOpSyncTrancheAccounting(
        Operation _op,
        NAV_UNIT _stPostOpRawNAV,
        NAV_UNIT _jtPostOpRawNAV,
        NAV_UNIT _stDepositPreOpNAV,
        NAV_UNIT _jtDepositPreOpNAV,
        NAV_UNIT _stRedeemPreOpNAV,
        NAV_UNIT _jtRedeemPreOpNAV
    )
        public
        override(IRoycoAccountant)
        onlyRoycoKernel
        returns (SyncedAccountingState memory state)
    {
        // For deposits, either ST or JT can deposit and increase the NAV (not both)
        // For withdrawals, ST and/or JT NAV can be withdrawn (coverage applied, yield sharing, IL repayments, etc.)
        // A simultaneous deposit and withdrawal is impossible
        require(
            ((_stDepositPreOpNAV > ZERO_NAV_UNITS ? 1 : 0) + (_jtDepositPreOpNAV > ZERO_NAV_UNITS ? 1 : 0)
                        + ((_stRedeemPreOpNAV > ZERO_NAV_UNITS || _jtRedeemPreOpNAV > ZERO_NAV_UNITS) ? 1 : 0)) == 1,
            INVALID_POST_OP_STATE(_op)
        );

        // Get the storage pointer to the accountant state
        RoycoAccountantState storage $ = _getRoycoAccountantStorage();

        // Cache the last checkpointed market state, effective NAV, and impermanent losses for each tranche
        NAV_UNIT stRawNAV = $.lastSTRawNAV;
        NAV_UNIT jtRawNAV = $.lastJTRawNAV;
        NAV_UNIT jtEffectiveNAV = $.lastJTEffectiveNAV;
        NAV_UNIT stEffectiveNAV = $.lastSTEffectiveNAV;
        NAV_UNIT stImpermanentLoss = $.lastSTImpermanentLoss;
        NAV_UNIT jtCoverageImpermanentLoss = $.lastJTCoverageImpermanentLoss;
        NAV_UNIT jtSelfImpermanentLoss = $.lastJTSelfImpermanentLoss;

        // Apply the effects of the actual operation that was executed (ST/JT deposit or withdrawal)
        if (_op == Operation.ST_DEPOSIT) {
            require(_stDepositPreOpNAV > ZERO_NAV_UNITS, INVALID_POST_OP_STATE(_op));
            // The raw NAV is meant to be increased by the ST NAV deposited
            stRawNAV = stRawNAV + _stDepositPreOpNAV;
            // New ST deposits are treated as an addition to the future ST exposure
            stEffectiveNAV = stEffectiveNAV + _stDepositPreOpNAV;
        } else if (_op == Operation.JT_DEPOSIT) {
            require(_jtDepositPreOpNAV > ZERO_NAV_UNITS, INVALID_POST_OP_STATE(_op));
            // The raw NAV is meant to be increased by the JT NAV deposited
            jtRawNAV = jtRawNAV + _jtDepositPreOpNAV;
            // New JT deposits are treated as an addition to the future loss-absorption buffer
            jtEffectiveNAV = jtEffectiveNAV + _jtDepositPreOpNAV;
        } else {
            require(_stRedeemPreOpNAV > ZERO_NAV_UNITS || _jtRedeemPreOpNAV > ZERO_NAV_UNITS, INVALID_POST_OP_STATE(_op));

            // The raw NAVs are meant to be decreased by the NAV withdrawn from each tranche
            if (_stRedeemPreOpNAV != ZERO_NAV_UNITS) stRawNAV = stRawNAV - _stRedeemPreOpNAV;
            if (_jtRedeemPreOpNAV != ZERO_NAV_UNITS) jtRawNAV = jtRawNAV - _jtRedeemPreOpNAV;

            if (_op == Operation.ST_REDEEM) {
                NAV_UNIT preWithdrawalSTEffectiveNAV = stEffectiveNAV;
                // The actual amount withdrawn from ST effective NAV could be from both tranches (its own share of its NAV, coverage applied, IL repayments, etc.)
                stEffectiveNAV = preWithdrawalSTEffectiveNAV - (_stRedeemPreOpNAV + _jtRedeemPreOpNAV);
                // The withdrawing senior LP has realized its proportional share of past uncovered losses and associated recovery optionality, rounding in favor of senior
                if (stImpermanentLoss != ZERO_NAV_UNITS) {
                    stImpermanentLoss = stImpermanentLoss.mulDiv(stEffectiveNAV, preWithdrawalSTEffectiveNAV, Math.Rounding.Ceil);
                }
                // The withdrawing senior LP has realized its proportional share of past JT losses from coverage applied and its associated recovery optionality, rounding in favor of senior
                if (jtCoverageImpermanentLoss != ZERO_NAV_UNITS) {
                    jtCoverageImpermanentLoss = jtCoverageImpermanentLoss.mulDiv(stEffectiveNAV, preWithdrawalSTEffectiveNAV, Math.Rounding.Floor);
                }
                // JT raw NAV that is leaving the market realized its proportional share of past JT losses from its own depreciation, rounding in favor of senior
                // If last JT raw NAV is zero, none of the JT exposure is leaving the market, so it is still entitled to 100% of it's self inflicted impermanent loss.
                if (jtSelfImpermanentLoss != ZERO_NAV_UNITS && $.lastJTRawNAV != ZERO_NAV_UNITS) {
                    jtSelfImpermanentLoss = jtSelfImpermanentLoss.mulDiv(jtRawNAV, $.lastJTRawNAV, Math.Rounding.Floor);
                }
            } else if (_op == Operation.JT_REDEEM) {
                NAV_UNIT preWithdrawalJTEffectiveNAV = jtEffectiveNAV;
                // The actual amount withdrawn from JT effective NAV could be from both tranches (its own share of its NAV, ST yield share, IL repayments, etc.)
                jtEffectiveNAV = preWithdrawalJTEffectiveNAV - (_stRedeemPreOpNAV + _jtRedeemPreOpNAV);
                // The withdrawing junior LP has realized its proportional share of past losses from coverage provided and associated recovery optionality, rounding in favor of senior
                if (jtCoverageImpermanentLoss != ZERO_NAV_UNITS) {
                    jtCoverageImpermanentLoss = jtCoverageImpermanentLoss.mulDiv(jtEffectiveNAV, preWithdrawalJTEffectiveNAV, Math.Rounding.Floor);
                }
                // JT raw NAV that is leaving the market realized its proportional share of past JT losses from its own depreciation, rounding in favor of senior
                // If last JT raw NAV is zero, none of the JT exposure is leaving the market, so it is still entitled to 100% of it's self inflicted impermanent loss.
                if (jtSelfImpermanentLoss != ZERO_NAV_UNITS && $.lastJTRawNAV != ZERO_NAV_UNITS) {
                    jtSelfImpermanentLoss = jtSelfImpermanentLoss.mulDiv(jtRawNAV, $.lastJTRawNAV, Math.Rounding.Floor);
                }
            }
        }

        // Checkpoint the mark to market NAVs and impermanent losses
        $.lastSTRawNAV = stRawNAV;
        $.lastJTRawNAV = jtRawNAV;
        $.lastSTEffectiveNAV = stEffectiveNAV;
        $.lastJTEffectiveNAV = jtEffectiveNAV;
        $.lastSTImpermanentLoss = stImpermanentLoss;
        $.lastJTCoverageImpermanentLoss = jtCoverageImpermanentLoss;
        $.lastJTSelfImpermanentLoss = jtSelfImpermanentLoss;

        // If any additional delta exists in the total raw and effective NAVs, it can attributed to rounding/dust losses in NAV: these must be treated as underlying PNL
        int256 totalNAVDelta = UnitsMathLib.computeNAVDelta((_stPostOpRawNAV + _jtPostOpRawNAV), (stEffectiveNAV + jtEffectiveNAV));
        if (totalNAVDelta != 0) return preOpSyncTrancheAccounting(_stPostOpRawNAV, _jtPostOpRawNAV);

        // NAV conservation is preserved: marshal the post-sync state and return
        state = SyncedAccountingState({
            // No state transition is possible in this branch since there is no PNL and NAV changes enforce coverage (ensuring LLTV can't be breached if it wasn't already in pre-op sync)
            marketState: $.lastMarketState,
            stRawNAV: _stPostOpRawNAV,
            jtRawNAV: _jtPostOpRawNAV,
            stEffectiveNAV: stEffectiveNAV,
            jtEffectiveNAV: jtEffectiveNAV,
            stImpermanentLoss: stImpermanentLoss,
            jtCoverageImpermanentLoss: jtCoverageImpermanentLoss,
            jtSelfImpermanentLoss: jtSelfImpermanentLoss,
            // No fees are ever taken if NAVs were conserved
            stProtocolFeeAccrued: ZERO_NAV_UNITS,
            jtProtocolFeeAccrued: ZERO_NAV_UNITS,
            // Additional data about the market's post-sync state
            utilizationWAD: UtilsLib.computeUtilization(_stPostOpRawNAV, _jtPostOpRawNAV, $.betaWAD, $.coverageWAD, jtEffectiveNAV),
            ltvWAD: UtilsLib.computeLTV(stEffectiveNAV, stImpermanentLoss, jtEffectiveNAV),
            fixedTermEndTimestamp: $.fixedTermEndTimestamp
        });

        emit TrancheAccountingSynced(state);
    }
```

## Finding Description:

Inside postOpSyncTrancheAccounting(), the contract handles post-operation NAV updates by applying both ST and JT raw NAV deltas.

During decrease operations ST_DECREASE_NAV and JT_DECREASE_NAV, the logic applies:

1. ST effective NAV updates using both deltaST and deltaJT

2. JT effective NAV updates using both deltaJT and deltaST

This mixes coverage transfers and withdrawal deltas into a single accounting path.

At the end of execution, only the sum of raw NAV and effective NAV is validated:

```solidity
require((_stRawNAV + _jtRawNAV) == (state.stEffectiveNAV + state.jtEffectiveNAV))
```

However, this invariant only verifies the total value and does not protect the correctness of the individual tranche balances. Because each tranche is updated independently with combined deltas and rounding behavior, it is possible for value to be redistributed between ST and JT while still satisfying the global NAV conservation check.

This allows internal tranche accounting corruption without triggering any revert.

## Impact Explanation:

This issue breaks core accounting guarantees of the protocol.

Consequences include:

1. Incorrect ST and JT effective NAV balances

2. Value shifting between tranches without real economic justification

3. Incorrect minting and redemption pricing

4. Broken coverage assumptions

5. Potential user fund loss

Since Royco relies on accurate tranche accounting for all downstream operations, this error propagates into pricing, withdrawals, and risk controls.

## Likelihood Explanation:

Medium (with realistic exploitation paths)

1. No privileged role is required

2. Triggered through normal protocol operations

3. Only requires reaching mixed delta execution paths

4. Deterministic and repeatable behavior

Attackers or edge-case flows can exploit this during post-operation state transitions.

## Proof of Concept:

Scenario:

1. ST and JT both experience negative raw NAV deltas during a post-operation sync (withdrawal combined with coverage movement).

2. The protocol applies:

. ST effective NAV update using (deltaST + deltaJT)

. JT effective NAV update using (deltaJT + deltaST)

3. Rounding behavior and ordering cause effective balances to shift.

4. Final check validates only:
```solidity
ST + JT total raw NAV == ST + JT total effective NAV
```
5. Individual tranche balances become inconsistent even though the global invariant passes.
This allows silent redistribution between tranches without reverting.

## Recommendation:

To prevent this issue:

1. Avoid applying mixed delta updates across tranche accounting paths

2. Enforce per-tranche invariants, not only global NAV conservation

3. eparate coverage transfers from withdrawal accounting

4. Add explicit checks that ST and JT effective balances remain individually consistent with their respective raw NAV changes

This ensures tranche isolation is preserved and prevents silent balance corruption.

## [H-05] Timestamp Based Yield Accrual Can Be Manipulated to Skew Tranche Yield Distribution

Target:
RoycoAccountant._accrueJTYieldShare()  
RoycoAccountant._previewSyncTrancheAccounting()  
https://github.com/roycoprotocol/royco-dawn/blob/main/src%2Faccountant%2FRoycoAccountant.sol#L563-L577

## Summary:

The protocol accrues Junior Tranche JT yield share using raw block.timestamp deltas. Because timestamp spacing is miner / builder influenced, this allows yield distribution to be manipulated by controlling the time gap between accrual and distribution calls.

An attacker or MEV enabled block builder can inflate JT’s accrued yield entitlement without any corresponding economic activity, resulting in unfair yield allocation between tranches.

```solidity
// RoycoAccount.sol

/// @dev STEP_DISTRIBUTE_YIELD: There are no remaining impermanent losses that ST yield is obligated to repay, the residual gains will be used to distribute yield to both tranches
            if (stGain != ZERO_NAV_UNITS) {
                // Compute the time weighted average JT share of yield
                uint256 elapsed = block.timestamp - $.lastDistributionTimestamp;
                // If the last yield distribution happened in the same block, use the instantaneous JT yield share. Else, use the time-weighted average JT yield share since the last distribution
                NAV_UNIT jtGain;
                if (elapsed == 0) {
                    // Get the instantaneous YDM output and ensure that JT cannot earn more than 100% of senior appreciation
                    uint256 instantaneousJtYieldShareWAD =
                        IYDM($.ydm).previewJTYieldShare($.lastMarketState, $.lastSTRawNAV, $.lastJTRawNAV, $.betaWAD, $.coverageWAD, $.lastJTEffectiveNAV);
                    if (instantaneousJtYieldShareWAD > WAD) instantaneousJtYieldShareWAD = WAD;
                    jtGain = stGain.mulDiv(instantaneousJtYieldShareWAD, WAD, Math.Rounding.Floor);
                } else {
                    jtGain = stGain.mulDiv(_twJTYieldShareAccruedWAD, elapsed * WAD, Math.Rounding.Floor);
                }
```

## Finding Description:

Yield accrual is performed in _accrueJTYieldShare() using:
```solidity
elapsed = block.timestamp - lastAccrualTimestamp;
twJTYieldShareAccruedWAD += jtYieldShareWAD * elapsed;
```

Later, this accumulated value is consumed inside _previewSyncTrancheAccounting() to split Senior Tranche (ST) yield:
```solidity
jtGain = stGain.mulDiv(_twJTYieldShareAccruedWAD, elapsed * WAD)
```

This design assumes timestamp progression is neutral and unpredictable. In practice:

1. Block producers can control timestamp spacing within protocol tolerance

2. MEV searchers can delay or reorder transactions

3. Yield distribution calls can be intentionally separated across blocks

This creates a direct lever to manipulate yield weighting without changing any on-chain economic state.

## Impact Explanation:

This issue breaks the fairness and correctness of tranche yield allocation.

Consequences include:

1. JT receiving inflated yield share

2. ST receiving reduced or delayed yield

3. Distorted protocol fee accounting

4. Incorrect economic assumptions for LPs

Over time, this enables silent value extraction and undermines confidence in tranche performance guarantees.

## Likelihood Explanation:

1. Does not require privileged access

2. Only relies on transaction timing and block inclusion behavior

3. MEV infrastructure already enables this class of manipulation

4. Repeatable and deterministic

## Proof of Concept:

A Foundry test demonstrates that increasing the timestamp gap before accrual directly amplifies JT yield share accumulation without any underlying NAV change.

Test Logic:

1. Advance timestamp by a small interval and accrue

2. Advance timestamp by a large interval and accrue again

3. Observe disproportionate growth in accumulated yield entitlement

The test confirms that yield accumulation scales directly with timestamp spacing and can be artificially inflated.

```solidity
function test_TimestampAccrualManipulation() public {

        accountant.exposed_accrue();
```

## Recommendation:

To mitigate this issue:

1. Avoid using raw block.timestamp directly for economic weighting

2. Cap maximum accrual windows

3. Normalize yield accrual into fixed accounting epochs

4. Use discrete checkpoint-based accounting instead of continuous time multiplication

5. Add sanity bounds on accumulated yield share growth

These changes remove timestamp-based manipulation vectors and reduce MEV influence on yield distribution.
